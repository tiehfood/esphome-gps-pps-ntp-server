P4 Timing Probe

A hardware-timestamped measurement instrument for the GPS/PPS stratum-1 NTP server — built because we can no longer measure our own improvements.

Target Waveshare ESP32-P4 ETH PoE Silicon rev 1.3 Framework ESP-IDF 5.5.1, bare app Status phases 1–6 done · server defect fixed, remaining errors traced · phase 7 paused
Why

The instrument is the bottleneck

The server's own GPS-referenced clock holds 4–6 µs. But every client we own reports it 60–100 µs away, and that number moved by 105 µs across one evening while the device itself never budged.

The cause is not the network. Moving the server onto the client's own network segment cut round-trip delay from 674 µs to 129 µs and left the offset unchanged. The clients are simply not references: one is disciplined by the very server it measures, the other tracks an internet stratum-1 with ±4 ms root distance.

So changes below roughly 20 µs are currently unfalsifiable. Last session's rate-term fix — a real correctness bug — could not be shown to help. This probe exists to end that.

The trap that would have faked Phase 3

On the P4 the driver passes a timestamp pointer on every frame — it is never NULL. Counting non-NULL pointers reported 86 of 86 frames stamped regardless. Only a zero stamp means "not latched", and only switching ts4all off and on within one boot proved the stamps were real.

The assumption that broke

The plan treated the probe's clock offset as constant across a measurement window. It is not: the free-running PTP clock gains 34.1 ppm on the GPS-disciplined server. It does so cleanly — R² 0.9999, the same slope to within 0.07 ppm across two runs, and the second run began 8.6 µs from where the first run's ramp predicted, 247 s later. So raw offsets are a ramp; removed, they are usable.

Per sample, the floor is not sub-microsecond — about 8 µs. As an A/B resolution it is: ±0.7 µs from 1000 samples per arm, roughly eight and a half minutes of exchanges. The samples are effectively independent, and the null test reports no effect when nothing changed. Resolution in an A/B comparison is what the plan's go/no-go actually needed.

Most of the per-sample noise is not the probe's. It moves offset by half the delay change in the opposite direction — the signature of a transmit timestamp stamped early — and the server's T3 is a prediction. The instrument is now seeing the device under test.

Found on the way

CONFIG_ETH_TRANSMIT_MUTEX defaults to off, and the DMA transmit ring has no lock of its own. Any second task transmitting alongside lwIP risks intermittent ring corruption that would look like a network fault. Enabled for the probe.

A first estimate of the server's internal latency also falls out: wire and store-and-forward account for about 30 µs of round trip, against 59 µs minimum and 114 µs median measured — roughly 30–85 µs spent inside the W5500 path.

Found

The noise was the server

The first live A/Bs came back at ±13 µs instead of the projected ±0.7 µs. The cause was not the probe: about 1% of the server's replies arrive in bursts that are wrong by milliseconds, and the instrument is precise enough to see exactly how.

The stalls were wall-clocked to second 7 of every minute, and a causal test settled what drives them: downloading the device's web page at second :30 produced a receive stall at :30 in four minutes out of four. Five candidate mechanisms were proposed and ruled out along the way, the last — the driver's 10 ms command-poll loop — by instrumenting it directly and counting zero retries. What starts the stall is still open.

The rate-term fix, measured

With the bursts excluded, switching the anchor's rate term moves offset by −3.11 ± 0.70 µs, and the legacy term leaves a +3.41 ± 1.75 µs sawtooth across each second that the hardware-measured rate removes — both inside the prediction written down before the run. Stated plainly: the analysis exactly as registered, with bursts included, was null; the confirmation needed a cleaning step that was not pre-registered.

What was changed on the server

  • Stalled requests are refused. The hardware-captured INTn edge already marked each frame's arrival; a request serviced ≥ 1 ms after it gets no reply. Clients retry.
  • The send estimate cannot be poisoned by a stall. Re-seeding needs rejects that agree with each other and a run longer than a stall lasts.
  • Per-request telemetry is throttled to one worst-case value per 10 s — it had been ~16 messages per second of the very load that causes stalls.
  • The driver's command handshake is instrumented from the existing SPI taps, without forking the driver.

Traced

Where the last errors come from

A diagnostics build, off by default behind a switch, recorded every request's receive and send timing on the server, plus 100 ms bins of every frame through the W5500. We ran four experiments: web load at second :30, 25 s of sustained downloads, and a logging A/B. The recordings were joined to the probe's hardware-stamped samples, 2,815 exchanges in all.

Two new defects

A wrong send estimate can last for minutes. The first send after boot took 2.6 ms and seeded the estimate. Sparse requests afterwards agreed with it, so it never re-seeded. When the probe's steady stream began (sends ~1.0 ms), 15 replies went out with T3 0.77 ms late before a re-seed. It is not idleness: after 0.25–60 s of silence, sends still take 1.04 ms. It is ordinary service, though. Overnight, with no test running, a quarter of the ten-second windows showed a reply leaving 1.5–1.75 ms after its T3. In a 20-minute passive capture, every slow send went to an SNTP-style client, one that leaves the transmit field empty, and SNTP clients set their clock from T3 alone. The cause is an ARP miss. For that client the server has no cached hardware address, so the reply waits in a queue while an ARP request goes out. All four slow sends sat next to the server's ARP request and its answer, where chance alone would give about 4%. All ten requests from SNTP-style clients triggered an ARP request, and none of the ten from other clients did. Worse, about half of these delays go unmeasured: the server records the ARP request's send, which looks normal, while the reply actually leaves later. So every reply to such a client carries an early T3. A second run from another host, with its prediction written down first, gave the same result: four of four slow sends next to an ARP exchange, and every ARP exchange from these clients.

The receive hook can match a stale request. Its 8-entry lookup returns the first entry with the same client transmit field and never checks age. A client that repeats that field, or leaves it zero, can be served a receive timestamp minutes old. Home Assistant's hook-latency history shows 11–574 s matches on both the old and new firmware.

What the verification also turned up

Some clients answer ARP slowly. A quarter of the requests in the passive run came from clients whose ARP reply took longer than the 20 ms wait, so they were refused. Every one of them asked again 3–4 s later and got a correct reply. No wrong timestamp went out, but they need one extra request each time.

The :07 burst was a switch setting, not firmware, and it's now fixed. Tagged broadcasts reaching the server meant its switch port forwarded other VLANs, and the W5500 can't filter those frames without also dropping ARP. After the port was restricted to its native VLAN, tagged frames fell from 20.5 per second to effectively none (4 frames in 10 minutes). Busy moments fell to a third, and what remains is ordinary mDNS.

Decisions taken. The stricter refusal rule is now on by default. The ARP wait stays at 20 ms: a longer wait would save slow clients one retry, but it would hold up every other client meanwhile and make the server easier to stall.

Still being checked: an overnight share of early-T3 windows, predicted at 2% or less against 24% before, and a day of receive-hook latency, predicted to stay under 1 s.

Measured

What the per-sample floor was made of

Once the stalls were gone, about 7 µs of noise remained in every single exchange. A robust fit across 2,772 exchanges split it cleanly. Almost all of it was the server predicting when its reply would leave: that prediction has 11.9 µs of jitter. Removing it left 1.95 µs. Also removing the small interrupt-to-read delay left about 1 µs for the network, the probe and its PHY together. The fit's coefficients matched the physics: −0.515 and +0.480 against −0.5 and +0.5, and +1.03 on delay.

Timing each reply's path showed where the jitter lives. Nearly all of it arises before the frame reaches the W5500; after the frame is written, only 3 µs remains before the chip is told to send. Separately, a hard cutoff in the late-receive cases pointed to the W5500 itself. The driver sets the chip to wait 1.75 ms before raising a new interrupt, and every late receive fell at or below 1.75 ms.

Where the two fixes stand

Late T3 is explained, and the explanation favours it. The old path wrote a T3 about 21 µs too early: its clock read came 16 µs before the send timer started, and the send itself ran 5 µs late. The patched T3 is early by only 3 µs. The offset shift therefore comes from removing a bias, not adding one. Late T3 is now the default: after the reboot all 29 of 29 test replies were patched, with no checksum errors at the client.

The shorter interrupt wait finally has a good trade. The first two attempts either refused about 30 requests that were probably on time, or accepted requests with nothing queued behind them, and 9 of 20 of those were late. What separated late from on-time was whether the request opened its own read burst. The third attempt accepts an edge-less request only then, and it passed every prediction written down before the run: late replies over 150 µs fell from 0.64% to 0.19% of all served, with 0.18 points more refusals and no stalls. It is now on by default, and the deployment check was better still: zero late replies in 469 served exchanges, with fewer refusals than before the change.

Turning it on by default needed a different safety net. Changing a chip register live has no separate way back if it goes wrong, so while this was an experiment it undid itself after 30 minutes unless told otherwise. A default cannot work that way — and simply dropping the timer would have been worse than leaving it off: had the change ever broken the receive path, every restart would have broken it again before a fix could be sent over the network, leaving a cable as the only way in. So the server now waits 60 seconds after each restart before applying it. That first minute always runs the stock settings, which guarantees a window in which the device can be reached and repaired remotely.

Constraint

What rev 1.3 costs us

Confirmed from the board

The P4 carries silicon revision 1.3. The EMAC's hardware PPS output requires rev ≥ 3, so there is no hardware path between the GPS pulse and the PTP clock. Every design choice here assumes that.

What survives is the part that matters most: per-frame TX and RX timestamps, captured in silicon at the start-of-frame delimiter on the RMII boundary. Against the current W5500 SPI taps — measured ~21 µs behind the earliest electrical indication — that is a change of three orders of magnitude.

The auxiliary snapshot input, which would have latched GPS PPS directly into the PTP clock, is absent at every revision: the registers exist in Espressif's headers but no pad reaches the trigger. Rev 3 would not have given us that either.

Theory

Delay is absolute; offset is not

This asymmetry shapes the entire design, so it is worth stating precisely.

δ = (T4 − T1) − (T3 − T2)

T1 and T4 are P4 time; T2 and T3 are server time. The clock offsets cancel algebraically. Only relative rate error survives, and across a ~1 ms round trip that is picoseconds.

A free-running P4 therefore measures round-trip delay to nanoseconds with no shared reference at all — which lets us compare measured delay against the physical minimum for a 90-byte frame at 100 Mbit and attribute the excess to device latency.

θ = ½[(T2 − T1) + (T3 − T4)] = θtrue + c

Here c is the P4's unknown clock offset. It does not cancel — but in an interleaved A/B it is constant across the window and drops out of the difference between the two arms.

Hence the split: absolute delay and differential offset come free in Phases 1–6. Absolute offset requires Phase 7, and lands softer.

The one gap

Our probes are NTP over UDP, so without ts4all the MAC stamps nothing we care about. esp_eth_mac_enable_ts4all() is master-only — but the low-level inline exists in 5.5.1 and emac_hal_ptp_start() simply never calls it. We set EMAC_PTP.timestamp_ctrl.en_ts4all ourselves: one register bit, reached through the linker-provided symbol. Considerably less invasive than the W5500 driver fork this project already carries.

Sequence

Seven phases, two gates

1

Bring-up

passed

Standalone ESP-IDF project outside the ESPHome tree. Internal EMAC with the IP101 over RMII, external 50 MHz clock in on GPIO50 — the arrangement that avoids the MPLL/PSRAM conflict that can fail EMAC init.

Done when the board takes a DHCP lease and answers ping from the Mac Studio.

2

PTP clock alive

passed

Enable timestamping through the ioctl interface and poll the clock.

Done when the PTP clock advances monotonically at 1 s/s with no rollover glitch between the seconds and nanoseconds registers.

3

ts4all and RX timestamps

risk gatepassed

Set the en_ts4all bit after ptp_start, register the receive callback, resolve the concrete type behind its void *info, and send the board an ordinary UDP packet.

Done when a hardware timestamp arrives for a non-PTP UDP frame and tracks the PTP clock. If it does not — stop here and reassess rather than build on it.

4

TX timestamps

passed

Transmit through the control path with a timestamp structure attached. The driver polls the descriptor for the stamp; Espressif's own comment notes a maximum of 31 loops observed on the P4 for a 1500-byte frame.

Done when every frame returns a plausible, monotonic stamp with no timeouts.

5

NTP probe

passed

Hand-built Ethernet/IP/UDP frame carrying a 48-byte NTP request, so transmission goes through the control path. Parse T2 and T3 from the reply; return raw quadruples over a UDP command interface.

Done when delay and offset computed on the Mac match the existing Python probe in magnitude, with visibly tighter scatter.

6

Characterise the floor

go / no-gopassed

Move the probe onto the server's own VLAN so no routed hop remains, then measure repeatability and compare delay against the computed physical minimum. Re-run the anchor A/B and the PPS rate-term change with the new instrument.

Done when we can state a defensible A/B resolution figure. This is the deliverable — if it is not well under 1 µs, Phase 7 is not worth building.

7

Absolute reference

Capture the GPS pulse on MCPWM at 6.25 ns, then correlate the MCPWM timebase to the PTP clock in software — paired reads with alternating order, plus back-to-back reads of each counter to measure and subtract the inter-read skew, so the residual is variability rather than a fixed bias.

Done when the PTP-versus-GPS offset holds ±1–5 µs, making the residual offset attributable and settling whether T3 is stamped early.

Stated plainly

Phase 7 cannot reach sub-microsecond on rev 1.3. With no hardware path from the capture timer to the PTP clock, the GPS link crosses software and carries a bias of order the register-read latency. The skew calibration removes the mean, not the variance. Against today's ~100 µs uncertainty it is still a twentyfold improvement — enough to settle the open question of whether T3 is stamped ~124 µs early — but it is not the nanosecond-grade reference a rev 3 board would allow.

Handover

Three things that need you

Move the probe's switch port

No longer needed. The probe's port already sits in the server's subnet, so there is no routed hop between them.

Wire the PPS split

Phase 7 needs the GPS pulse on a free P4 pin — signal plus a ~100 Ω series resistor and a ground wire. Both boards run on PoE and are galvanically isolated; without the ground reference the measurement is meaningless.

Pick the input pin

A free GPIO, avoiding the RMII set (34, 35, 28, 29, 30, 49), MDC 31, MDIO 52, PHY power 51 and clock-in 50.
