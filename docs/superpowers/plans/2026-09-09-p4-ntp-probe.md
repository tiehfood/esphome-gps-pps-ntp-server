# ESP32-P4 Hardware-Timestamped NTP Probe — Implementation Plan

**Goal:** Build a measurement instrument that drops our NTP A/B noise floor from ±19 µs to
sub-microsecond, and gives a ±1–5 µs absolute reference, so firmware changes to the S3 NTP
server become measurable instead of unfalsifiable.

**Architecture:** A bare ESP-IDF app on a Waveshare ESP32-P4 ETH PoE. The P4's EMAC stamps
NTP request/reply frames in hardware at the SFD. The P4 stays dumb — it returns raw
`(T1,T2,T3,T4)` quadruples over UDP; all statistics, interleaving and A/B control live in
Python on the Mac Studio.

**Tech stack:** ESP-IDF 5.5.1, ESP32-P4 (rev 1.3), IP101 PHY over RMII, MCPWM capture,
Python 3 on the Mac for control/analysis.

---

## Global Constraints

- **ESP-IDF 5.5.1** — the version already on this machine (`~/.platformio/packages/framework-espidf`).
- **Silicon is rev 1.3** → `esp_eth_mac_set_pps_out_gpio()` is unavailable (needs rev ≥ 3).
  Every design choice below assumes no hardware PPS output.
- **No ESPHome** for the probe. Bare IDF app, separate build tree from `ntp_server.yaml`.
- **Must not disturb the S3 server, Home Assistant, the Pi, or the Mac Studio.** The probe is
  a client; the only write it performs against the S3 is the existing A/B switch over HTTP.
- Board pins (verified from Waveshare wiki + ESPHome P4 defaults):
  RMII data `34 TXD0, 35 TXD1, 28 RX_CRS_DV, 29 RXD0, 30 RXD1, 49 TX_EN`;
  `MDC 31`, `MDIO 52`, `PHY power 51`, `CLK_EXT_IN 50`, `phy_addr 1`.
- **No AI attestation** in commits (repo rule).

## Measurement Theory — why this works

**Round-trip delay is absolute with no shared clock.**

    δ = (T4 − T1) − (T3 − T2)

T1/T4 are P4 time, T2/T3 are S3 time; the clock *offsets* cancel algebraically. Only relative
*rate* error survives, and over a ~1 ms round trip that is picoseconds. So a free-running P4
measures δ to nanoseconds. This alone lets us compare measured delay against the physical
minimum (serialization + switch store-and-forward + PHY) and attribute the excess to device
latency.

**θ is differential without a reference.** θ = θ_true + c, where c is the P4's unknown clock
offset. In an interleaved A/B, c is constant across the window and cancels in the difference.

**θ becomes absolute (±1–5 µs) in Phase 7** by measuring the P4 PTP clock against GPS PPS.
That link crosses software, so it carries a constant bias equal to the inter-register read
skew. Mitigation: time back-to-back reads of each counter to measure the skew directly, and
alternate read order so the residual is variability rather than mean.

## Phases

### Phase 1 — Bring-up
- [x] Create `p4probe/` as a standalone ESP-IDF project (not in the ESPHome tree). PlatformIO,
      `framework = espidf`, board `esp32-p4-evboard`; gitignored.
- [x] Configure Ethernet: internal EMAC, IP101, RMII, `CLK_EXT_IN` on GPIO50, pins above.
      `ETH_ESP32_EMAC_DEFAULT_CONFIG()` already matches this board exactly — no pin overrides.
- [x] Flash, confirm link up + DHCP lease. Link at 2.4 s, `192.168.34.172` (same /24 as the S3).
- [x] **Chip revision: v1.3** — boot log and esptool agree.

**Result 2026-09-10: PASSED.** Mac Studio ping 30/30, then 600/600 at 5/s.
- **Acceptance:** the P4 pings, and `ping` from the Mac Studio succeeds.

### Phase 2 — PTP clock alive
- [x] `ioctl(ETH_MAC_ESP_CMD_PTP_ENABLE)` — takes a `bool*`; config is hardcoded internally
      (XTAL, 25 ns period, 40 ns accuracy, FINE, digital rollover). Tick is 40 ns, not selectable.
- [x] Poll `G_PTP_TIME` in a loop; log seconds/nanoseconds.

**Result 2026-09-10: PASSED.** Steady-state steps 999 999 960 / 1 000 000 000 / 1 000 000 040 ns
— the 40 ns tick. These time the report task against the PTP clock, so they prove monotonic
counting and clean rollover, not crystal accuracy (both share the 40 MHz XTAL). Note: a PTP
read returns zeros with ESP_OK while timestamping is off — gate reporting on it being enabled.
- **Acceptance:** the PTP clock advances monotonically at ~1 s/s, no rollover glitches.

### Phase 3 — `ts4all` and RX timestamps (**the risk gate**)
- [x] After `ptp_start`, set `EMAC_PTP.timestamp_ctrl.en_ts4all = 1` (declare `extern emac_ptp_dev_t EMAC_PTP;`).
      Disassembly confirms: `lui/addi → 0x50098700 <EMAC_PTP>`, read, `ori 256` (bit 8 = TSENALL), write.
- [x] Register via `esp_eth_update_input_path_info()`; `info` is `eth_mac_time_t*`.
- [x] Plain non-PTP traffic (DHCP, ARP, ICMP ping from the Mac Studio).

**Result 2026-09-10: PASSED — with a trap found on the way.**
- **`info` is never NULL on P4** (`esp_eth_mac_esp.c:457`, compile-time `&ts`, passed on every
  frame). Counting non-NULL pointers reports 100% regardless. **Zero stamp = not latched.**
- **Control experiment, one boot, ping at 5/s:** ts4all toggled every 10 s, four windows.
  With the bit set, stamps advance and fall inside the preceding PTP second. With it clear,
  every frame still arrives but the stamp is `0.000000000`. Setting it again restores real
  stamps on the very next frame. Reproduced on both cycles. Ping 600/600 throughout.
- Conclusion: `ts4all` is exactly what makes the MAC capture SFD stamps on non-PTP frames.
- **Acceptance:** a hardware RX timestamp arrives for a **non-PTP** UDP frame, and it tracks
  the PTP clock. If this fails, stop and reassess — everything downstream depends on it.

### Phase 4 — TX timestamps
- [x] Transmit via `esp_eth_transmit_ctrl_vargs()` with `ctrl` pointing at an `eth_mac_time_t`.
- [x] Confirm the returned stamp is plausible against the PTP clock.
- **Acceptance:** TX stamps returned for every frame, monotonic, no timeouts.

**Prerequisite found: `CONFIG_ETH_TRANSMIT_MUTEX=y`.** It defaults to `n`, and
`esp_eth_transmit_ctrl_vargs()` only locks when it is set, while the DMA code rewrites the TX
descriptor ring with no lock of its own. lwIP transmits through the same function, so a probe
task sending concurrently could corrupt the ring. With the mutex, the TX-stamp busy-poll runs
inside the lock (lwIP transmits wait for it, sub-ms).

How the driver delivers the stamp (`esp_eth_mac_esp_dma.c:292-304`): with PTP enabled every
TX descriptor requests one, but it is only collected when a `ctrl` pointer is passed, by
busy-polling the last descriptor up to 50 iterations. **Timeout silently zero-fills** — same
sentinel as RX.

**Result 2026-09-10: PASSED.** 90-byte frames (NTP-request size) at 10 Hz to an unowned
locally-administered MAC (the S3's W5500 MAC filter drops it in silicon), EtherType 0x88B5,
with ping at 5/s from the Mac Studio competing for the transmitter:
- 500 frames: **0 timeouts, 0 unbracketed, 0 non-monotonic, 0 send errors.**
- Steady state (min / median / max): read-before → SFD **15.6 / 16.0 / 17.5 µs**;
  SFD → read-after 14.2 / 14.5 / 15.0 µs; call 28 / 29 / 30 µs. Boot window had one 64 µs
  lead during DHCP: contention showing as latency, not corruption.
- Ping 1100/1100, RX still 100% stamped.
- PTP-time bracket (≈30.5 µs) and `esp_timer` call duration (29 µs) agree.

Takeaway: a software T1 taken just before transmit would carry **~16 µs systematic error**
on this board; the hardware T1 removes it. PHY latency (MII SFD → copper) is not visible to a
single device and remains a Phase 7 concern.

### Phase 5 — NTP probe
- [x] Hand-build Ethernet/IP/UDP + 48-byte NTP request (mode 3, VN 4), sent through the ctrl
      path. IPv4 and UDP checksums computed (the ESP EMAC driver never enables checksum insertion).
      **Next hop learned from the reply, not from lwIP's ARP table:** `etharp_find_addr()` would
      race the tcpip thread (`CONFIG_LWIP_TCPIP_CORE_LOCKING` is off). One ordinary NTP request
      goes out through a lwIP socket; the RX hook takes the reply's Ethernet source MAC —
      the server on-link, the gateway if routed, i.e. always the correct next hop.
- [x] Parse T2/T3 from the reply; assemble `(T1,T2,T3,T4)` with hardware T1/T4. Matched by a
      cookie in the transmit field (T1 does not exist until the frame leaves).
      **Probe replies are consumed in the RX hook** (`free(buffer)`): no lwIP socket owns the probe
      port, so forwarding them would make lwIP send ICMP port-unreachable to the device under test.
- [x] UDP command interface on 12300: `PING`, `RUN <ip> <count> <gap_ms>` → `Q` lines + `END`.
      The same priming reply steps the PTP clock once to the NTP era (offsets in µs, not a century).
- **Acceptance:** δ and θ computed on the Mac agree in magnitude with the existing Python
  probe (δ ≈ 130–800 µs depending on path), with visibly lower scatter.

**Result 2026-09-10: PASSED.** Client `p4client.py` (Mac Studio `/root/ntp/`), exact integer ns.
- Run 1: 200/200 ok, run 2: 300/300 ok — 0 timeouts, 0 TX/RX zero stamps, 0 rejects.
  Next hop `98:a3:16:c0:3b:83` = the S3's W5500. T3−T2 2416 µs (Pi measured 2411 µs).
- δ median **114.9 / 114.4 µs**, IQR 21.4 / 19.9 µs (same /24). Reference kernel-stamped Mac
  Studio client, routed: 241.5 µs, offset IQR 18.6 µs.
- **Raw θ is a ramp, not noise.** The free-running PTP clock runs at **+34.106 / +34.180 ppm**
  against the GPS-disciplined server (R² 0.99973 / 0.99990). Run 2 began −8.6 µs from where
  run 1's ramp predicts across a 247 s gap. So the design assumption "c is constant across a
  window" was wrong: c ramps, but linearly and repeatably, so it is removable.
- **Detrended θ:** IQR 10.4 / 9.4 µs, std 8.2 / 7.5 µs — below the kernel-stamped reference, but
  not sub-µs per sample.
- **Attribution:** detrended θ regressed on δ has slope −0.52 / −0.41, corr −0.93 / −0.83.
  That is the signature of T3 stamped early (or return-path queuing): δ +e, θ −e/2. T3 is a
  *prediction* on the S3, so the dominant residual is most likely the device under test,
  which this instrument can now see.

### Phase 6 — Characterise the floor (**go/no-go for Phase 7**)
- [x] Place the P4 on the S3's VLAN so there is no routed hop. **No change needed:** the P4's
      port already sits in the S3's /24 (DHCP `192.168.34.172`).
- [x] Run long captures; report median/IQR of δ and θ, and the short-term stability.
- [x] Compare measured δ against the computed physical minimum for 90-byte frames at 100 Mbit.
- **Acceptance:** a stated, defensible A/B resolution figure. Target: well under 1 µs.
- [ ] Re-run the anchor A/B and the PPS-rate-term change with the new instrument.

**Floor result 2026-09-10** (runs 1+2, 188 + 283 samples after delay-outlier exclusion;
scripts `p4trend.py`, `p4decomp.py`, `p4acf.py` in `/root/ntp/` on the Mac Studio):

| quantity | run 1 | run 2 |
|---|---|---|
| detrended θ std / IQR | 8.18 / 10.44 µs | 7.45 / 9.42 µs |
| of which delay-coupled (T3 signature) | 7.64 µs (slope −0.52) | 6.21 µs (slope −0.41) |
| remainder std / IQR | 2.92 / 3.45 µs | 4.13 / 4.49 µs |
| integrated autocorrelation time | 1.00 | 1.13 |

- **Verdict against the target, stated both ways.** Per sample the floor is **not** sub-µs
  (std ~8 µs, most of it the server's T3 prediction). As an **A/B resolution it is**: ±0.7 µs
  at 1000 samples per arm (~8.5 min of exchanges at 4 Hz), with samples effectively
  independent and the A/A null test reporting no false effects. The A/B resolution is what
  the plan's go/no-go needs.
- The A/B figure uses the FULL detrended residual. The delay-coupled split only bounds the
  noise; subtracting delay from an A/B effect would absorb genuine T2/T3 changes.
- **Lead, not a conclusion:** run 1 has ρ(lag 4 = 1 s) = +0.20 and ρ(lag 6) = −0.21; run 2 shows
  +0.10 at lags 4 and 8. A per-second structure in the remainder is where the S3's adjtime
  sawtooth would appear. Confirming needs T2-phase data the current CSVs lack.
- **Physical delay bound (estimate).** 100 Mbit = 80 ns/byte. Outbound: remaining 94 B of the
  frame after the P4's SFD stamp (7.5 µs) + switch egress incl. preamble (8.2 µs). Return:
  full frame into the switch (8.2 µs) + preamble to the P4's SFD (0.6 µs). ≈ 24.5 µs plus
  switch forwarding twice → **~30 µs**. Measured δ min 58.7 µs, median ~114 µs → roughly
  **30–85 µs inside the S3's W5500 receive/transmit path** (T2 lateness + SEND-to-wire).
  First time that sum has been measurable.

**Server defect: root cause (2026-09-10).**

*Timing.* Wall-clocked across three runs (`p4clock.py`): every minute at second 4.6–7.5 (mostly
7.0) a ~1 s receive stall, 50–114 ms per request; every T3-late burst follows one. HA publish
seconds: uptime :02.4, gps_pps_time :03.5, debug :04.8 — none matches.

*Refuted along the way* (each by source or data): flash/NVS access in `update()`; debug heap walk;
missed W5500 interrupt with a ~100 ms poll fallback (interrupt mode re-checks after 1000 ms, and
`poll_timer` exists only in polling mode); main-loop CPU starvation (main task core 0 prio 1,
ntp_recv core 1 prio 7, w5500_tsk prio 15, tcpip prio 18); transmit waiting for W5500 TX space
(it returns ESP_ERR_NO_MEM instead).

*Device-side corroboration* (`/events`): the S3's own `NTP T3 Prediction Error` jumps to 0.4–3.5 ms
and `Hook Latency` to 3.4–7.1 ms right after each stall, and its outbound TCP goes silent ~1 s
then flushes.

*Causal test* (`p4load.py`):
- **A — 5 concurrent web-page downloads (≈390 KB) at second :30 of each minute: a receive stall
  at :30.0–:30.1 in 4 of 4 minutes (140 / 99 / 37 / 94 ms)**, alongside the natural :07 ones.
  Outbound TCP load through the W5500 stalls the receive path on demand.
- B — probe at 1 s, no injected load: the :07 stall persists (the probe does not create it) but
  only 2 of 5 minutes were caught, 7.7 / 14.4 ms. Inconclusive on magnitude: 1 sample/s can
  miss the peak of a ~1 s stall.

*Candidate mechanism (source-level, unproven):* `w5500_send_command()` serves SEND and also the
RECV issued after every received frame; if Sn_CR has not cleared on the first read-back the
caller sleeps 10 ms per retry, up to 100 ms. The 140 ms peak means it cannot be the whole story.

*Self-inflicted load:* the S3 publishes t3_error / int_lead / rx_stamp_gap / hook_latency on every
request (~16 messages/s at a 4 Hz probe) over API and SSE.

*Client impact:* stage 1 — ~1 s per minute of replies with T2 up to ~100 ms late (up to +50 ms
offset; SNTP clients accept them). Stage 2 — stalled SENDs reseed `send_us_`, giving 3–5 replies
with T3 1.4–2.9 ms late and negative delay, which min-delay clock filters prefer.

*Fix options:* harden the T3 reseed (only reseed on mutually consistent rejects); refuse requests
whose arrival-to-handling time exceeds a threshold; throttle per-request telemetry; count Sn_CR
retries to prove the mechanism before touching the vendored driver.

**Fixes implemented 2026-09-10** (all four chosen; one reflash that also restores
`pps_interval_ppb`; verification with `p4verify.py` pending):

- *Refuse stalled requests.* The arrival reference already existed: `eth_input_hook_()` computes
  `int_lead = burst_start - MCPWM INTn edge` (normally 3–25 us) but recorded it only below 20 ms —
  which is why "NTP INT Lead" went silent during every stall. Now `rx_stalled = int_lead >= 1000 us`
  (edges older than 2 s untrusted) is stored in the seqlocked hook ring, and `recv_task_()` drops
  the request and counts it (`refused` sensor). No reply is sent, so a stalled request can no
  longer feed the T3 estimate either.
- *Harden the T3 re-seed.* A re-seed now needs `SEND_RESEED_AFTER` rejects that agree with each
  other within `SEND_STEP_MAX_US` **and** a run spanning at least 3 s (a stall lasts ~1 s). It seeds
  to the run's centre instead of the last sample.
- *Throttle telemetry.* `hook_latency`, `rx_stamp_gap`, `t3_error` and `int_lead` publish every 10 s
  as the window's largest-magnitude value (lock-free accumulators), instead of on every request.
  Their meaning changes from "last request" to "worst in 10 s"; `int_lead` now shows stalls.
- *Instrument the command handshake without vendoring the driver.* The fork's SPI taps see every
  `Sn_CR` write (the command byte) and every `Sn_CR` read-back (its value), so they count completed
  commands, commands needing more than one poll (each a 10 ms sleep), the longest write-to-cleared
  time, and overlapping commands. New sensors `w5500_cmd_retries`, `w5500_cmd_max`.

Built and compiled against the repo test config with no warnings in our code. Before flashing, the
deployed components on the SMB share were checked against git HEAD (`ntp_server`, `ethernet`) and
the working tree (`gps_pps_time`), so the flash ships only these changes.

  The every-minute +18…+48 ms replies are gone.
- **The Sn_CR sleep-loop hypothesis is refuted by direct measurement:** `w5500_cmd_retries` stayed 0

- **`pps_interval_ppb` is restored** (9187–9250 ppb).
- **Open 1 — transmit stall:** one reply at 21:23:30.2 UTC with 80.3 ms delay and −38.1 ms offset (T3

  the S3 records nothing: sends longer than `SEND_US_MAX` are discarded silently.
- **Open 2 — small receive-late replies:** nine 1.4–5.3 ms T2-late replies were not refused, so their

- **Open 3 — reseed hardening is untested:** neither run triggered a reseed, so this comparison
  cannot show its effect.
- **Correction:** `p4verify.py` reported robust σ 71 µs because it fitted the drift ramp with ordinary
  least squares including the ms spikes, tilting the slope. Refit robustly (`p4compare.py`) the floor
  is 6.87 µs.

### Phase 7 — Absolute reference (±1–5 µs, expectations set above)
- [ ] Identify a free GPIO on the board for PPS input (avoid RMII/PSRAM/flash pins).
- [ ] Wire GPS PPS → P4 GPIO **with a series resistor (~100 Ω) and a common ground wire**.
      Both boards are PoE-powered and therefore isolated; the ground wire establishes the
      shared reference. Keep the cable short.
- [ ] MCPWM capture (group 0, PLL160M → 6.25 ns) on the PPS edge.
- [ ] Correlate the MCPWM timebase to the PTP clock: paired reads with **alternating order**,
      plus back-to-back reads of each counter to measure and subtract the read skew.
- [ ] Publish the PTP-vs-GPS offset alongside each NTP quadruple.
- **Acceptance:** PTP-vs-GPS offset stable to ±1–5 µs; the residual θ against the S3 becomes
  attributable, testing the "T3 stamped ~124 µs early" hypothesis.

## Risks and Open Items

1. **Phase 3 is the gate.** If `ts4all` does not produce RX stamps for plain UDP, the design
   needs rethinking (fallback: newer ESP-IDF with `esp_eth_mac_enable_ts4all()`).
2. **`info` payload type** behind the RX callback — resolve by reading `esp_eth.c` at implementation.
3. **`ptp_start` may clear `en_ts4all`** — set it after, and re-verify after any link event.
4. **Free GPIO for PPS** — must be confirmed against the Waveshare pinout.
5. **PoE isolation** — the ground wire is required, not optional.
6. **IP101 PHY TX/RX latency asymmetry is uncharacterised** by anyone. It bounds absolute
   accuracy below ~1 µs and cannot be calibrated without a better reference. Affects Phase 7
   only; Phases 1–6 are unaffected because delay and differential θ do not depend on it.
7. **Rev 1.3 is confirmed** — no hardware PPS out. If a rev ≥ 3 board is ever obtained, Phase 7
   is replaced by a pure-hardware differential capture and should reach tens of nanoseconds.
